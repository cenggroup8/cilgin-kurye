\msection{Purpose}

M6 is the admin screen. On one page the admin starts and controls the game, changes all parameters
during play, puts obstacles on a live map, starts earthquakes and watches the results as live graphs.
Each change can be seen in three places: in the 3D city on the phones, on the LED board, and in the
graphs on this page.

\ckinfo{adm}{Browser on the main computer, or a laptop on the game Wi-Fi. The page comes from M2}{TypeScript web page, a light chart library for the live graphs, a 2D drawing of the city for the live map, MessagePack messages over one WebSocket}{R6 R7 R9 R10 R11}

The admin page talks only to M2, over one WebSocket that needs the admin password. The figure shows
what the page gets and what it sends.

the map needs fewer updates.

\msection{Main components}

The page is made of five parts. The communication manager is the only part that talks to M2.

\begin{longtable}[]{|L{0.21}|L{0.39}|L{0.40}|}
\hline \textbf{Component} & \textbf{Takes} & \textbf{Gives} \\ \hline \endhead
Communication manager & Messages from M2, commands from the other parts & Decoded data for each part, reconnect and full update after a lost link \\ \hline
Parameter manager & Parameter list with limits, admin input & Forms built from the list, changes with a ``pending'' mark until the reply \\ \hline
Map manager & Game state, clicks on the map & The live map, and obstacle commands with road, lane and position \\ \hline
Graph engine & Metrics, board samples, change marks & Live graphs, the seismic graph, CSV files \\ \hline
Top bar and earthquake panel & Phase, time, board status, button presses & Game commands, earthquake command, the event log \\ \hline
\end{longtable}

\msub{Parameters}
The parameters are in groups: game, obstacles, players, physics, earthquake, network (one set for
each player) and board link. When the page opens, it asks M1 for all parameters with their limits and
builds the forms from this list, so a new parameter needs no new page code. A slider sends its value
only when it stops moving, so one drag does not send many messages. Until the server answers, the
value is marked ``pending''. If the answer is ``ok'', the mark goes away. If the answer is an error,
the slider goes back to the old value and the log shows the reason.

\msub{Network settings}
The network group has one row for each player and one for the board. In each row the admin sets an
added delay, a jitter and a loss chance, and for a phone also a frame rate limit. M2 applies these
values at once. The ping, jitter and loss graphs show the result next to the change mark.

\msub{Cause and effect}
The main goal of the panel is to show the effect of a change. So every change puts a thin vertical
line on all graphs, with the name of the parameter. For example, when the admin sets more traffic,
the line appears and the graph of the mean NPC speed goes down right after it. At the same time the
phones show more cars and the board shows more red. The graph data can be saved as a CSV file for the
report.

\msub{Adding an obstacle}
The admin first chooses a tool, for example the road work brush. Then the admin clicks on a road on
the live map. The map manager finds the nearest road segment, the lane and the position on it with the
numbering of the city plan. The communication manager sends an ``add obstacle'' command with the type,
road, lane and position. M1 checks that the road exists and that the obstacle limit is not reached.
Then it adds the obstacle to the list and raises the version number. In the next tick the obstacle is
in the game state, so the map, the phones and the board show it at the same time. The eraser sends a
``remove obstacle'' command in the same way. ``Close road'' puts road work on a whole segment, and
``in front of a player'' puts the chosen obstacle a little ahead of that player's motorcycle.

\msub{Earthquake}
The start button sends a command to M1, and M1 asks the board to run its motors. If the board is not
connected, M1 makes the earthquake by itself. The seismic graph shows the sensor signal of the board
live, 100 samples per second. Each earthquake event puts a mark on the graph with its strength and
zone. A hand hit on the board shows on the same graph, so the admin can compare the two.

\msub{After a lost link}
If the WebSocket breaks, the page shows a grey bar and tries to connect again. After the new login,
M2 sends the full parameter list, the current game state and the recent history of all graphs that
M1 keeps. So the page fills the forms, the map and the graphs again and the admin can go on at once.

\msection{Testing}

M6 is tested alone against a fake server that plays back a recorded game with its metrics, parameter
list and board data. We check every parameter form with good and wrong values, every map tool, all
graphs and the CSV export, a wrong password, a second admin login, and that after a lost link the
forms, the map and the graphs are complete again.
